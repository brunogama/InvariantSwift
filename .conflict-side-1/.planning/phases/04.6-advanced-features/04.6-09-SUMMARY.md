## Technical Decisions

### Decision 1: Comprehensive Examples Over Brevity

**Choice:** Include full, syntactically correct code examples for every feature

**Rationale:**
- Documentation must be copy-pasteable
- Reduces friction for developers learning features
- Prevents "documentation drift" (examples are verifiable)

**Implementation:**
- All code blocks use proper Swift syntax
- Import statements included where necessary
- Examples compile and demonstrate real usage

**Alternatives Considered:**
- Prose-only descriptions: rejected (not actionable)
- Pseudo-code: rejected (ambiguity in API usage)

### Decision 2: Cross-Referencing Strategy

**Choice:** Bidirectional links between MACROS.md, COOKBOOK.md, and GENERATORS.md

**Rationale:**
- Features span multiple documentation files
- Enable discovery from any entry point
- Reduce duplication (each file has specific focus)

**Implementation:**
- COOKBOOK.md links to MACROS.md for macro details
- MACROS.md describes "what", COOKBOOK.md shows "how"
- GENERATORS.md links to related macros and cookbook patterns

**Alternatives Considered:**
- Isolated documentation: rejected (poor discoverability)
- Single mega-file: rejected (overwhelming, hard to navigate)

### Decision 3: Section Organization

**Choice:** Feature-based organization (not API-based)

**Rationale:**
- Developers think in terms of features ("how do I add timeout?")
- Not API types ("what does PropertyConfig do?")
- Cookbook structure: problem → solution

**Implementation:**
- COOKBOOK.md: "Timeout Control" section (feature-oriented)
- Not: "PropertyConfig Reference" (API-oriented)
- Each section starts with use case, then shows solution

**Alternatives Considered:**
- Alphabetical: rejected (doesn't match mental model)
- Type-based: rejected (scatters related features)
