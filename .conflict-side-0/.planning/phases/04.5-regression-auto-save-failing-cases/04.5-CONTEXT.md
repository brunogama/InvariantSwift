# Phase 4.5: @Regression — Auto-Save Failing Cases - Context

**Gathered:** 2026-01-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Implement @Regression macro to automatically save failing test cases to the example database with replay-first capability. This phase delivers automatic regression test preservation through counterexample persistence, bridging property-based testing (ephemeral) with regression testing (persistent).

The macro integrates with @PropertyTest to capture failures, serialize inputs, persist to database, and replay before random generation.

</domain>

<decisions>
## Implementation Decisions

### Database Persistence Strategy
- **File format:** JSON (human-readable) for easy inspection and debugging
- **Storage location:** Test-target specific (`.invariant/{TestTarget}.json`) — separate database per test target for isolation
- **Serialization:** Custom serialization via protocol (`RegressionSerializable`) to support non-Codable types with fallback to Codable
- **Database schema:** Flat array of failures `[{testName, inputHash, serializedInput, timestamp, failureReason}]` — fast appends, linear search acceptable for 100-failure cap

### Replay Behavior and Ordering
- **Replay timing:** Always replay first (before random generation) — deterministic behavior
- **Replay order:** Insertion order (oldest first) — FIFO: failures replayed in discovery order
- **Passed failures:** Remove from database (auto-cleanup) — fixed bugs automatically removed; database stays lean
- **Random generation:** Skip if all replays pass — trust that replays are sufficient; faster test execution

### Failure Identification and Deduplication
- **Unique ID:** Hash of serialized input (SHA256) as unique identifier — fast lookup, handles duplicates
- **Deduplication:** Yes, store each unique input once — saves space; if same input fails twice, only store once
- **Metadata:** Store timestamp (when failure occurred) + failure reason/message — track when discovered and why it failed
- **Hash collisions:** Ignore collisions (accept risk) — SHA256 collision probability is ~0; not worth complexity
- **Failure grouping:** No, treat each input independently — simple: each failure is unique, no grouping logic
- **Same input, different errors:** Treat as separate failures — different errors = different bugs; store both
- **Iteration tracking:** No, just record that it failed — simple: failure is binary, don't track iteration count

### Database Lifecycle and Management
- **Automatic expiration:** Yes, remove failures older than 30 days — configurable TTL keeps database lean
- **Maximum size:** Cap at 100 failures per test — oldest pruned when exceeded
- **Manual pruning:** Provide CLI command (`swift package prune-regression-db --test TestName`) for user control
- **Database migration:** Auto-migrate silently — detect old schema, migrate automatically, no user action needed
- **Concurrency:** Yes, use file locking — multiple tests can write concurrently; prevent corruption with file locks

### Claude's Discretion
- Exact hashing algorithm implementation details (use Swift's built-in CryptoKit)
- File locking mechanism (NSFileLock, flock, or custom)
- Error messages for serialization failures
- Database file format versioning strategy

</decisions>

<specifics>
## Specific Ideas

- Database file naming: `.invariant/{TestTargetName}.regression.json` (not just `{TestTarget}.json` to allow for future database types)
- TTL cleanup runs lazily on database load (not a background thread) for simplicity
- Per-test cap (100 failures) enforced at write time: if exceeded, remove oldest failure before appending new one
- CLI command naming follows SPM plugin conventions: `swift package plugin --plugin InvariantSwiftPlugin prune-regression-db`
- Serialization protocol: `public protocol RegressionSerializable { func serialize() throws -> Data; static func deserialize(from: Data) throws -> Self }`
- Hash collisions: Accept negligible risk (~1 in 2^256); no fallback comparison logic to keep implementation simple

</specifics>
