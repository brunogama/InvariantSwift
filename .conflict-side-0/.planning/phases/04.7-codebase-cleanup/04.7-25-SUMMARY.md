## Decisions Made

### 1. Builder Pattern (Not Fluent API)

**Decision:** Use traditional builder pattern (constructor + build()) instead of fluent API (.withX().withY().build())

**Rationale:**
- Report construction is one-shot operation (not incremental/chainable)
- Fluent API adds unnecessary verbosity for this use case
- Constructor captures all parameters, build() does the work - clearer intent

**Alternative Considered:** Fluent API pattern
**Why Rejected:** RunReport construction doesn't benefit from method chaining (unlike Property tests with .cover().classify().label())

### 2. ReportMetadata Parameter Object

**Decision:** Group propertyName, durationMs, config, shrinkTrace into `ReportMetadata` struct

**Rationale:**
- Reduces buildReport parameter count from 5 to 2
- Satisfies SwiftLint `function_parameter_count` rule (warn at 4, error at 6)
- Cohesive grouping - all metadata relates to test execution context

**Impact:** buildReport signature cleaner, meets code quality budgets

### 3. FailureContext in RunReportBuilder

**Decision:** Introduce private `FailureContext` struct to group failure case parameters

**Rationale:**
- buildFailureReport originally had 5 parameters (counterexample, shrunk, iterations, reason, seed)
- Grouping into single object reduces to 1 parameter
- Private to RunReportBuilder - implementation detail, not part of API

**Impact:** All RunReportBuilder methods now have ≤ 2 parameters

## Technical Notes

### Why Builder Pattern Works Here

RunReport construction has 3 distinct cases (success, failure, gaveUp), each requiring different data:
- **Success:** iterations only
- **Failure:** counterexample, shrunk, iterations, reason, seed, shrinkTrace
- **GaveUp:** discarded, iterations

Builder pattern allows:
1. Single entry point (constructor) captures common parameters
2. `build()` method switches on result, delegates to case-specific helpers
3. Each helper method stays small and focused

### SwiftLint Budget Management

This refactoring demonstrates budget-based coding (RULES.md):

**Before:**
- buildReport: 83 lines (exceeds 60-line warning threshold)
- buildReport: 5 parameters (exceeds 4-parameter warning threshold)
- Required 2 disable markers to suppress warnings

**After:**
- buildReport: 13 lines (well under 60)
- buildReport: 2 parameters (under 4)
- All helpers: under 40 lines
- All helpers: under 4 parameters
- Zero disable markers needed

### Type Safety with Generics

RunReportBuilder uses generic parameter `<T>` to maintain type safety:
- `result: PropertyResult<T>` - preserves original generic type
- `counterexample: T` and `shrunk: T` in FailureContext - type-safe access
- No type erasure needed (unlike initial approach with `Any`)

## Lessons Learned

### 1. Parameter Objects Beat Long Parameter Lists

Introducing `ReportMetadata` and `FailureContext` made code more maintainable:
- Easier to add new metadata fields without changing signatures
- Self-documenting (grouped parameters have clear semantic relationship)
- Satisfies SwiftLint budgets without artificial splitting

### 2. Builder Pattern for Multi-Case Logic

When a function has multiple complex cases (success/failure/gaveUp), builder pattern allows:
- Case-specific logic in dedicated methods
- Shared setup in constructor
- Clean separation of concerns

### 3. Budget-First Refactoring Works

By targeting SwiftLint budgets early (60-line functions, 4-parameter limit), we avoided:
- Technical debt accumulation
- Future "big bang" refactorings
- Disable marker proliferation
