# Phase 04.3: @Equivalence Macro — Function Equivalence Testing - Research

**Researched:** 2026-01-23
**Domain:** Swift macro implementation, function equivalence testing, floating-point comparison
**Confidence:** HIGH

## Summary

Function equivalence testing is a well-established pattern in property-based testing frameworks (QuickCheck's `===`, Hypothesis's `@equivalent`, fast-check's `compareEqualTo`). The @Equivalence macro automates comparing two function implementations (reference vs candidate) across randomly generated inputs, essential for safe refactoring and algorithm optimization.

InvariantSwift already has 90% of the required infrastructure:
- **DifferentialTesting.swift** provides `DifferentialTester<Input, Output>` with error behavior modes and custom comparers
- **DifferentialTestMacro.swift** implements `@DifferentialTest` macro (stub implementation, extraction logic complete)
- **FloatingPointMode.swift** provides `FloatingPointTolerance<T>` with `.absolute()`, `.relative()`, and `.ulp()` strategies
- **PropertyMacro.swift** demonstrates the complete peer macro pattern for generating Swift Testing-compatible tests

The implementation follows established patterns from existing macros. Research confirms this is a straightforward integration task rather than novel feature development.

**Primary recommendation:** Leverage existing `@DifferentialTest` infrastructure and extend with tolerance parameter for floating-point comparisons. Follow `@PropertyTest` macro architecture for code generation.

### Pattern 1: Peer Macro with Swift Testing Integration
**What:** Generate a `@Test` function that compares reference and candidate implementations
**When to use:** All function equivalence tests
**Example:**
```swift
// Source: PropertyMacro.swift (lines 7-49)
public struct EquivalenceMacro: PeerMacro {
  public static func expansion(
    of node: AttributeSyntax,
    providingPeersOf declaration: some DeclSyntaxProtocol,
    in context: some MacroExpansionContext
  ) throws -> [DeclSyntax] {
    // 1. Extract function signature
    guard let funcDecl = declaration.as(FunctionDeclSyntax.self) else {
      context.diagnose(Diagnostic(
        node: node,
        message: MacroError.onlyApplicableToFunction
      ))
      return []
    }

    // 2. Extract parameters
    let parameters = ParameterExtractor.extract(from: funcDecl)

    // 3. Build wrapper enum with @Test function
    let wrapperEnum = buildWrapperEnum(
      original: funcDecl,
      parameters: parameters,
      config: extractConfig(from: node)
    )

    return [DeclSyntax(wrapperEnum)]
  }
}
```

### Pattern 2: Tolerance-Aware Comparison
**What:** Use `FloatingPointTolerance<T>` for approximate equality when Output is Float/Double
**When to use:** Comparing floating-point function outputs
**Example:**
```swift
// Source: FloatingPointMode.swift (lines 204-220)
public func isApproximatelyEqual(
  to other: Self,
  tolerance: FloatingPointTolerance<Self>
) -> Bool {
  if handleSpecialValues(other) { return true }

  switch tolerance {
  case .absolute(let epsilon):
    return abs(self - other) <= epsilon

  case .relative(let factor):
    let maxMagnitude = max(abs(self), abs(other))
    guard maxMagnitude > 0 else { return true }
    return abs(self - other) / maxMagnitude <= factor

  case .ulp(let distance):
    return countULPSteps(to: other, maxSteps: distance)
  }
}
```

### Pattern 3: DifferentialTester Integration
**What:** Reuse existing `DifferentialTester<Input, Output>` for comparison logic
**When to use:** All equivalence tests
**Example:**
```swift
// Source: DifferentialTesting.swift (lines 164-200)
public struct DifferentialTester<Input: Sendable, Output: Sendable>: Sendable {
  public let reference: @Sendable (Input) throws -> Output
  public let candidate: @Sendable (Input) throws -> Output
  public let comparer: (@Sendable (Output, Output) -> Bool)?

  public func test(_ input: Input) -> DifferentialResult<Input, Output> {
    let refResult = Result { try reference(input) }
    let candResult = Result { try candidate(input) }

    return DifferentialResult(
      input: input,
      referenceOutput: refResult,
      candidateOutput: candResult,
      comparer: comparer
    )
  }
}
```

### Anti-Patterns to Avoid
- **String interpolation for code generation:** Use AST builders (FunctionDeclSyntax, etc.) exclusively
- **Force unwrapping optionals:** Use guard/if-let pattern with diagnostics
- **Ignoring generic type constraints:** Ensure Output: Equatable or custom comparer provided
- **Manual float comparison:** Leverage FloatingPointTolerance instead of raw epsilon checks

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Float comparison | `abs(a - b) < epsilon` | `FloatingPointTolerance<T>` | Handles NaN, ±∞, signed zero, ULP distance correctly |
| Test generation | Manual @Test functions | `@PropertyTest` pattern | Swift Testing integration, failure reporting, shrinking |
| AST construction | String interpolation | SwiftSyntax AST builders | Type-safe, trivia-preserving, compiler-verified |
| Error divergence | Custom error matching | `ErrorBehavior` enum | Supports 4 modes: mustMatch, bothThrowOrBothSucceed, candidateMaySucceedMore, ignoreErrors |
| Generic constraints | Manual type checking | SwiftSyntax type extraction | Handles where clauses, associated types correctly |

**Key insight:** InvariantSwift's existing infrastructure handles all edge cases. Custom solutions will miss IEEE 754 edge cases, error handling modes, and shrinking integration.

## Common Pitfalls

### Pitfall 1: Floating-Point Edge Cases
**What goes wrong:** Naive epsilon comparison fails on NaN, infinity, signed zero
**Why it happens:** IEEE 754 special values have non-intuitive equality semantics:
- `NaN != NaN` (breaks reflexivity)
- `+0.0 == -0.0` but `1.0 / +0.0 != 1.0 / -0.0`
- `abs(∞ - ∞)` is `NaN`, not 0
**How to avoid:** Always use `FloatingPointTolerance<T>` with explicit handling of special values
**Warning signs:** Test failures on edge inputs (0.0, very large numbers, division by zero)

### Pitfall 2: Generic Type Inference Complexity
**What goes wrong:** Compiler cannot infer function type from closure expression
**Why it happens:** Swift's type inference struggles with higher-order function types in macro context
**How to avoid:**
1. Start with concrete function signatures (`(Int) -> Int`)
2. Extract types from function declaration parameters explicitly
3. Build type annotations using SwiftSyntax rather than relying on inference
**Warning signs:** "Cannot infer type" errors during macro expansion

### Pitfall 3: Tolerance Parameter Type Safety
**What goes wrong:** User passes `tolerance: 0.0001` for non-floating-point Output types
**Why it happens:** Macro doesn't validate Output type matches tolerance type
**How to avoid:**
1. Check if Output type is BinaryFloatingPoint before allowing tolerance parameter
2. Emit diagnostic if tolerance specified for non-float types
3. Use overloads: `@Equivalence(...)` vs `@Equivalence(tolerance: ...)`
**Warning signs:** Compile errors in generated code referencing `isApproximatelyEqual`

### Pitfall 4: String Interpolation in AST Generation
**What goes wrong:** Generated code has syntax errors, trivia loss, or escaping issues
**Why it happens:** String interpolation bypasses Swift's type system and AST validation
**How to avoid:** NEVER use `DeclSyntax(stringLiteral: ...)`. Always use AST builders:
```swift
// WRONG
return DeclSyntax(stringLiteral: "func test() { ... }")

// RIGHT
return DeclSyntax(FunctionDeclSyntax(
  name: .identifier("test"),
  signature: FunctionSignatureSyntax(...),
  body: CodeBlockSyntax { ... }
))
```
**Warning signs:** Macro expansion tests fail, SwiftLint violations in generated code

### Pitfall 5: Missing Sendable Conformance
**What goes wrong:** Compiler errors about non-Sendable closure captures in generated code
**Why it happens:** Swift 6 strict concurrency requires all closures to be `@Sendable`
**How to avoid:**
1. Mark all closure parameters `@escaping @Sendable`
2. Ensure Input and Output types are Sendable
3. Use `@unchecked Sendable` only when absolutely necessary (not needed here)
**Warning signs:** Concurrency errors during macro expansion or test compilation

```swift
// Source: PropertyMacro.swift (lines 7-49), adapted
public struct EquivalenceMacro: PeerMacro {
  public static func expansion(
    of node: AttributeSyntax,
    providingPeersOf declaration: some DeclSyntaxProtocol,
    in context: some MacroExpansionContext
  ) throws -> [DeclSyntax] {
    let ctx = MacroContext(context: context)

    guard let funcDecl = declaration.as(FunctionDeclSyntax.self) else {
      ctx.error(EquivalenceMacroDiagnostic.mustBeFunction, at: node)
      return []
    }

    // Extract parameters: func testEquiv(reference: F, candidate: F)
    let parameters = ParameterExtractor.extract(from: funcDecl)
    guard parameters.count == 2 else {
      ctx.error(EquivalenceMacroDiagnostic.requiresTwoParameters, at: funcDecl.signature)
      return []
    }

    let config = EquivalenceConfigExtractor.extract(from: node)

    let wrapperEnum = buildWrapperEnum(
      original: funcDecl,
      parameters: parameters,
      config: config
    )

    return [DeclSyntax(wrapperEnum)]
  }
}
```

### Test Wrapper Generation
```swift
// Source: PropertyMacro.swift (lines 55-105)
private static func buildWrapperEnum(
  original funcDecl: FunctionDeclSyntax,
  parameters: [ExtractedParameter],
  config: EquivalenceMacroConfig
) -> EnumDeclSyntax {
  let enumName = "\(funcDecl.name.text)_EquivalenceTest"
  let testName = funcDecl.name.text

  let testFunc = FunctionDeclSyntax(
    attributes: AttributeListSyntax {
      AttributeSyntax(
        attributeName: IdentifierTypeSyntax(name: .identifier("Test")),
        leftParen: .leftParenToken(),
        arguments: .argumentList(
          LabeledExprListSyntax {
            LabeledExprSyntax(expression: StringLiteralExprSyntax(content: testName))
          }
        ),
        rightParen: .rightParenToken()
      )
    },
    modifiers: DeclModifierListSyntax {
      DeclModifierSyntax(name: .keyword(.static))
    },
    funcKeyword: .keyword(.func),
    name: .identifier("run"),
    signature: buildThrowsSignature(),
    body: buildTestBody(parameters: parameters, config: config)
  )

  return EnumDeclSyntax(
    modifiers: DeclModifierListSyntax {
      DeclModifierSyntax(name: .keyword(.private))
    },
    name: .identifier(enumName),
    memberBlock: MemberBlockSyntax(
      members: MemberBlockItemListSyntax {
        MemberBlockItemSyntax(decl: testFunc)
      }
    )
  )
}
```

## Open Questions

Things that couldn't be fully resolved:

1. **Generic Function Type Inference**
   - What we know: Swift type inference struggles with higher-order function types
   - What's unclear: Whether we can support fully generic `<T, U> (T) -> U` or need concrete signatures initially
   - Recommendation: Start with concrete types (`(Int) -> Int`), validate with type extraction tests, expand to generics incrementally

2. **Tolerance Parameter for Non-Float Types**
   - What we know: FloatingPointTolerance only works for BinaryFloatingPoint types
   - What's unclear: Should we reject tolerance parameter at macro expansion time or compile time?
   - Recommendation: Emit diagnostic during macro expansion with clear message: "tolerance parameter only valid for Float/Double outputs"

3. **Integration with @Reproduce for Failing Equivalences**
   - What we know: @Reproduce macro can replay specific failing inputs
   - What's unclear: How to serialize function references (reference/candidate) for reproduction
   - Recommendation: Phase 04.3 focuses on equivalence testing; defer @Reproduce integration to Phase 04.5 (@Regression)
