## Decisions Made

### 1. Custom SwiftLint Configuration for Test Suites

**Decision:** User created custom `.swiftlint.yml` in `Tests/InvariantSwiftTests/FunctionalTesting/` that disables `file_length`, `type_body_length`, and `line_length` rules (commit 666123e).

**Rationale:**
- Comprehensive test suites legitimately exceed standard limits
- Tests prioritize completeness over brevity
- Similar approach used in Macro tests directory

**Impact:**
- Allows comprehensive test files like `ComprehensiveGeneratorTests.swift` (600+ lines)
- Maintains strict linting for production code
- Establishes pattern for test-specific linting configurations

### 2. Targeted Disables for Mathematical Properties

**Decision:** Use `swiftlint:disable:next` for specific patterns that are valid in testing context.

**Examples:**
- `identical_operands` for reflexivity tests (`x == x`)
- `large_tuple` for multi-parameter property test generators
- Always include explanatory comments

**Impact:**
- Maintains lint strictness while allowing mathematically valid test patterns
- Self-documenting code (comments explain why pattern is intentional)
- Avoids false positives for valid testing practices

## Implementation Notes

### Custom SwiftLint Configuration

The user created `Tests/InvariantSwiftTests/FunctionalTesting/.swiftlint.yml`:

```yaml
disabled_rules:
  - file_length          # Comprehensive test suites exceed 400 lines
  - type_body_length     # Test struct bodies exceed 300 lines
  - line_length          # Long test descriptions and assertions
```

This resolved cascading formatting conflicts where swift-format would make changes that created new violations.

### Formatting vs Linting Conflicts

**Challenge:** swift-format and SwiftLint had competing preferences for closure formatting:
- SwiftLint: wants parameters on same line as opening brace
- swift-format: puts parameters on new line for long signatures

**Solution:** Used multi-line initializer format:
```swift
let property = Property<[Int]>(
  generator: Gen<[Int]>.array(Gen<Int>.int(in: 0...100))
) { array in
  !array.contains(42)
}
```

This satisfies both tools by breaking at the initializer level rather than the closure level.
