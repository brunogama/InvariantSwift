# Phase 4.7: Codebase Cleanup - Research

**Researched:** 2026-01-24
**Domain:** Swift code quality, linting, refactoring
**Confidence:** HIGH

## Summary

This research investigates the current state of technical debt in the InvariantSwift codebase, specifically:
- 395+ SwiftLint disable markers across 60+ source and test files
- 127 active SwiftLint violations in strict mode
- 16 disabled test files (`.swift.disabled`)
- ~13 failing tests related to coverage infrastructure

The cleanup requires a systematic approach: first fix compiler warnings and SwiftLint violations in source code, then address test files, and finally re-enable disabled tests. The primary challenge is that many violations are in legitimately complex macro code (AST builders) and data-heavy files (domain generators) that may need architectural refactoring rather than simple fixes.

**Primary recommendation:** Process cleanup in dependency order - fix Sources/ first (enables test compilation), then fix Tests/, then re-enable disabled tests one-by-one after verifying APIs match.

## Architecture Patterns

### Pattern 1: Extract Print Statements to Dedicated Methods

**What:** Move print statements to dedicated methods that can be conditionally compiled or disabled.

**When to use:** Files with multiple `no_print` disables (23 files, 109 instances)

**Example:**
```swift
// Before (multiple disables throughout)
// swiftlint:disable:next no_print
print("Debug: \(value)")

// After (single disable, centralized)
private func debugLog(_ message: @autoclosure () -> String) {
  #if DEBUG
  // swiftlint:disable:next no_print
  print(message())
  #endif
}

debugLog("Debug: \(value)")
```

### Pattern 2: Split Large Files by Responsibility

**What:** Split files exceeding 400 lines into focused modules by responsibility.

**When to use:** Files with `file_length` violations (15 files)

**Example:**
```
// Before: Property.swift (2469 lines)

// After:
Property.swift           // Core Property type (~300 lines)
Property+Combinators.swift  // Combinator operators
Property+Evaluation.swift   // Evaluation logic
Property+Printing.swift     // Debug printing
PropertyRunner.swift        // Already separate
```

### Pattern 3: Extract Helper Functions

**What:** Extract complex logic into small, focused helper functions.

**When to use:** Functions exceeding 60 lines or complexity > 10

**Example:**
```swift
// Before: 89-line function with complexity 17
func processGeneration(...) {
  // validation
  // setup
  // main logic with many branches
  // result handling
}

// After: Composed small functions
func processGeneration(...) {
  try validate(...)
  let context = setupContext(...)
  let result = executeGeneration(context, ...)
  return handleResult(result, ...)
}

private func validate(...) throws { ... }          // 10-15 lines
private func setupContext(...) -> Context { ... }  // 10-15 lines
private func executeGeneration(...) { ... }        // 20-30 lines
private func handleResult(...) { ... }             // 10-15 lines
```

### Pattern 4: Parameter Objects for Long Parameter Lists

**What:** Replace functions with >4 parameters with a parameter object struct.

**When to use:** Files with `function_parameter_count` violations (15 files, 27 instances)

**Example:**
```swift
// Before: 8 parameters
func extractTypeInfo(
  decl: DeclSyntax,
  context: MacroExpansionContext,
  name: String,
  members: [MemberDeclListItemSyntax],
  inheritance: [InheritanceClauseSyntax],
  attributes: [AttributeSyntax],
  genericParams: [GenericParameterSyntax]?,
  whereClause: WhereClauseSyntax?
) { ... }

// After: Parameter object
struct TypeExtractionRequest {
  let decl: DeclSyntax
  let context: MacroExpansionContext
  let name: String
  let members: [MemberDeclListItemSyntax]
  let inheritance: [InheritanceClauseSyntax]
  let attributes: [AttributeSyntax]
  let genericParams: [GenericParameterSyntax]?
  let whereClause: WhereClauseSyntax?
}

func extractTypeInfo(_ request: TypeExtractionRequest) { ... }
```

### Pattern 5: Strategy Pattern for Complex Switch Statements

**What:** Replace long switch/if-else chains with dictionary-based dispatch or strategy protocols.

**When to use:** Functions with high cyclomatic complexity from branching (12 files, 25 instances)

**Example:**
```swift
// Before: switch with 15 cases, complexity 17
func processNode(_ node: SyntaxKind) {
  switch node {
  case .struct: ...
  case .class: ...
  case .enum: ...
  // 12 more cases
  }
}

// After: Dictionary dispatch
private let nodeProcessors: [SyntaxKind: (Syntax) -> Result] = [
  .struct: processStruct,
  .class: processClass,
  .enum: processEnum,
  // ...
]

func processNode(_ node: SyntaxKind, syntax: Syntax) -> Result {
  guard let processor = nodeProcessors[node] else {
    return .unsupported
  }
  return processor(syntax)
}
```

### Anti-Patterns to Avoid

- **Blanket disables:** Never use `// swiftlint:disable rule` at file level without `:next` or `:this`
- **Superfluous disables:** Remove disables for rules that no longer trigger
- **Copy-paste disables:** Don't propagate disables; refactor the underlying code
- **Disable without justification:** Always include a brief reason why the disable is necessary

## Common Pitfalls

### Pitfall 1: Breaking API Compatibility
**What goes wrong:** Refactoring public types/methods breaks downstream code
**Why it happens:** Focus on internal structure without checking public surface
**How to avoid:** Check for `public` access level before renaming/splitting
**Warning signs:** Type/method names in public documentation, exports in FunctionalTesting.swift

### Pitfall 2: Incomplete Refactoring
**What goes wrong:** Splitting a file but forgetting internal dependencies
**Why it happens:** Private/internal methods referenced across split boundaries
**How to avoid:** Build after each split, fix errors immediately
**Warning signs:** Compiler errors about undefined symbols after split

### Pitfall 3: Over-Refactoring
**What goes wrong:** Creating too many tiny files/functions that hurt readability
**Why it happens:** Trying to hit arbitrary line limits exactly
**How to avoid:** Stay comfortably under limits (80% of threshold), not at edge
**Warning signs:** Functions with only 1-2 lines, files with only 1 small type

### Pitfall 4: Fixing Tests Before Sources
**What goes wrong:** Tests fail because source APIs changed
**Why it happens:** Wrong dependency order
**How to avoid:** Always fix Sources/ completely before Tests/
**Warning signs:** Test compilation errors, undefined symbols

### Pitfall 5: Re-enabling Tests Without Verification
**What goes wrong:** Re-enabled tests fail because APIs changed since disabling
**Why it happens:** Assuming disabled tests will "just work"
**How to avoid:** Compile each test file in isolation, update APIs before renaming
**Warning signs:** `.swift.disabled` files with old import statements

3. For remaining violations, apply refactoring patterns
4. Run `swift build -Xswiftc -warnings-as-errors` to verify

**Priority order:**

5. `type_body_length` (5) - Split large types
6. `line_length` (10) - Break long lines

### Phase 3: Tests After Sources Stable

**Order:**
1. Fix InvariantSwiftTests (core test suite)
2. Fix InvariantSwiftMacroTests (macro tests)
3. Fix CoverageIntegrationTests (infrastructure tests)
4. Fix InvariantSwiftDomainGeneratorsTests

### Phase 4: Re-enable Disabled Tests

**Process per file:**
1. Rename `.swift.disabled` to `.swift`
2. Run `swift build --target [test-target]` to check compilation
3. Fix import statements and API calls
4. Run specific test to verify it passes
5. If test needs significant updates, document why

## Code Examples

### Removing Blanket Disables

```swift
// Before (blanket disable)
// swiftlint:disable no_print file_length function_body_length type_body_length

struct CatalogBrowser { ... }

// After (targeted disables or refactored)
// At type declaration if genuinely needed:
// swiftlint:disable:next type_body_length
struct CatalogBrowser {
  // swiftlint:disable:next function_body_length
  func largeFunction() { ... }
}
```

### Handling Orphaned Doc Comments

```swift
// Before (triggers orphaned_doc_comment)
/// Some documentation
// swiftlint:disable:next some_rule
func foo() { ... }

// After (combine into single doc comment block)
/// Some documentation
///
/// - Note: Disable reason: [explanation]
// swiftlint:disable:next some_rule
func foo() { ... }
```

### Fixing for_where Violations

```swift
// Before
for item in items {
  if item.isValid {
    process(item)
  }
}

// After
for item in items where item.isValid {
  process(item)
}
```

### Fixing identical_operands (Intentional in Tests)

```swift
// These are intentional reflexivity tests - use inline disable
@Test("Reflexivity property")
func testReflexivity() {
  // swiftlint:disable:next identical_operands
  #expect(value == value)  // Intentional: testing reflexivity
}
```
