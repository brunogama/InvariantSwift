# Phase 4.1: Refactor Fakery to Domain Data - Research

**Researched:** 2026-01-23
**Domain:** Data generation, domain data collections, test data generation
**Confidence:** HIGH

## Summary

Phase 4.1 addresses the vendor-specific naming of "Fakery" in InvariantSwift's domain data generators. The current implementation (`InvariantSwiftDomainGenerators` module) already provides a complete, self-contained fake data generation system with NO external dependencies. However, the terminology "Faker" and "Fakery" in public API names creates vendor perception issues, suggesting dependency on external libraries like `vadymmarkov/Fakery`.

The research reveals that InvariantSwift's implementation is actually vendor-neutral and self-contained, but needs API renaming to reflect this. The module provides comprehensive domain data generation (100+ generator types across 15 categories), locale support (25+ locales), and proper integration with Gen<T> shrinking strategies.

**Primary recommendation:** Rename public API from `Gen.faker()` to `Gen.domainData()` or `Gen.data()` while preserving all existing functionality and data collections.

### Pattern 1: Embedded Data Collections
**What:** Self-contained data arrays per locale, lazy-loaded on first access
**When to use:** Always (avoids external dependencies and file I/O)

```swift
// Source: FakerData.swift
public final class FakerData: @unchecked Sendable {
  public static let shared = FakerData()
  private var loadedLocales: [FakerLocale: LocaleData] = [:]
  private let lock = NSLock()

  public func data(for locale: FakerLocale) -> LocaleData {
    lock.lock()
    defer { lock.unlock() }
    if let cached = loadedLocales[locale] {
      return cached
    }
    let data = LocaleData.create(for: locale)
    loadedLocales[locale] = data
    return data
  }
}
```

### Pattern 3: Generator Integration with Shrinking
**What:** Domain data generators that shrink like primitive generators
**When to use:** All domain data - preserves property-based testing semantics

```swift
// Source: FakerGenerator.swift
extension Gen where T == String {
  public static func faker(_ type: FakerType, locale: FakerLocale = .default) -> Gen<String> {
    switch type {
    case .email:
      // Shrinks by reducing component complexity
      return Gen { rng, _ in
        let first = data.firstNames.randomElement(using: &rng)?.lowercased() ?? "user"
        let last = data.lastNames.randomElement(using: &rng)?.lowercased() ?? "example"
        let domain = data.emailDomains.randomElement(using: &rng) ?? "example.com"
        return "\(first).\(last)@\(domain)"
      }

  }
}
```

### Anti-Patterns to Avoid
- **External Dependencies**: Don't introduce faker library dependencies (breaks self-containment)
- **File I/O for Data**: Don't load data from JSON/YAML files (impacts performance and portability)
- **Non-Shrinkable Generators**: Domain data must shrink appropriately for minimal failing examples
- **Vendor-Specific Naming**: Public APIs should be vendor-agnostic (no "Faker", "Fakery")

## Common Pitfalls

### Pitfall 1: Breaking Existing Tests
**What goes wrong:** Renaming public APIs breaks all existing test code using `Gen.faker()`
**Why it happens:** `Gen.faker()` is used extensively in tests (606 test assertions across FakerTests.swift)
**How to avoid:** Provide deprecated aliases with migration warnings
**Warning signs:** Compilation errors in test suites after renaming

**Mitigation:**
```swift
// Provide deprecated aliases
extension Gen {
  @available(*, deprecated, renamed: "domainData")
  public static func faker(_ type: FakerType, locale: FakerLocale = .default) -> Gen<String> {
    domainData(type, locale: locale)
  }
}
```

### Pitfall 2: Inconsistent Naming Across Layers
**What goes wrong:** Renaming only public API but keeping internal "Faker" names
**Why it happens:** Fear of breaking internal implementation
**How to avoid:** Systematic rename across all layers (files, types, functions, tests)
**Warning signs:** Mixed terminology in codebase ("FakerData" but "Gen.domainData")

**Solution:** Rename comprehensively:
- `Faker/` → `Data/` or `DomainData/`
- `FakerType` → `DomainDataType`
- `FakerLocale` → `DataLocale` or keep (locale concept is universal)
- `FakerData` → `DomainDataStore`
- `FakeryGenerators` → `DataGenerators`

### Pitfall 3: Over-Engineering the Migration
**What goes wrong:** Attempting major functionality changes during naming refactor
**Why it happens:** Temptation to "improve while we're here"
**How to avoid:** Separate concerns - rename first, enhance later
**Warning signs:** Scope creep beyond API renaming

**Stay Focused:**
1. Phase 4.1: Rename API (vendor neutrality)
2. Future phase: Enhance functionality (if needed)

### Pitfall 4: Loss of Locale Data During Refactor
**What goes wrong:** Moving files breaks locale data references
**Why it happens:** String-based locale lookups in data creation
**How to avoid:** Comprehensive test coverage + validation
**Warning signs:** Test failures in locale-specific tests

**Validation:**
```swift
// Ensure all locales still load after refactor
@Test("All locales load successfully")
func allLocalesLoad() {
  for locale in DataLocale.allCases {
    let data = DomainDataStore.shared.data(for: locale)
    #expect(!data.firstNames.isEmpty)
    #expect(!data.lastNames.isEmpty)
  }
}
```

## Open Questions

Things that couldn't be fully resolved:

1. **Should we keep "fake" in the fluent API?**
   - What we know: `Gen.fake.name.firstName` is intuitive
   - What's unclear: Is "fake" vendor-neutral enough?
   - Recommendation: Keep it - "fake data" is common terminology, not vendor-specific
   - Alternative: `Gen.data.name.firstName` (more neutral but less clear)

2. **What about ISP-0010 proposal references?**
   - What we know: ISP-0010 is titled "Faker Integration" throughout codebase
   - What's unclear: Should proposal be renamed?
   - Recommendation: Add note to ISP-0010 that "Faker" refers to fake data pattern, not external library

3. **Should FakerLocale be renamed?**
   - What we know: "Faker" in type name suggests external dependency
   - What's unclear: "DataLocale" vs "GeneratorLocale" vs keep "FakerLocale"
   - Recommendation: Rename to `DataLocale` for consistency

4. **Timeline for deprecation removal?**
   - What we know: Need deprecated aliases for migration
   - What's unclear: When to remove deprecated names?
   - Recommendation: 2 major versions - deprecate in 1.x, remove in 3.0
